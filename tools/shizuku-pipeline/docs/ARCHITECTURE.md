# ARCHITECTURE.md — 設計思想と構造

対象読者: このパイプラインを保守・拡張する人／AIエージェント。
「なぜこう作ったか」を記す。手順は `MANUAL.md`、契約は `SPEC.md`。

## 1. 解きたい問題

しずくのwikiには2つの更新対象がある。
- **年表ページ**: 出来事の時系列（`* YYYY-MM-DD：出来事<ref>` 形式）。
- **紹介ページ**: 機能・スペック・人物像の紹介（「特殊機能」節など）。

原資料は増え続けるログ。YouTube配信ごとに字幕(SBV/SRT)・ライブチャット・概要(info)・事後コメント、
加えてXの月次TSVログ。これを**定期的に・取りこぼしなく・出典付きで**wikiへ反映したい。
ただしwikiは公開物であり、誤りや捏造は許されない。

## 2. 中心にある3つの原則

### 原則1: 字幕は「索引」、逐語は人間の耳
YouTube自動字幕(ASR)は固有名詞を安定して壊し（「あき先生」→「秋先生」等）、非言語音（舌打ち・鳴き真似・笑い声）は
そもそも文字に写らない。だからASRは「どのあたりで何が起きたか」を指す**索引**として使い、
名言の逐語は必ず人間が該当時刻を試聴して確定する。これを機械が代行しない（**ゲート1**）。
`t` 付きのYouTube URL（`https://www.youtube.com/live/<vid>?t=<秒>`）が索引から試聴への橋になる。

### 原則2: 拾う基準は「重要度」でなく「型」、判定は遅延させる
配信中の発話が後で「名言」や「回収」になるかは、その時点では分からない。
だから抽出時は**型**（出来事/名言候補/伏線/機能/人物情報/配信ノート）で機械的に拾い、
「重要かどうか」の判定は、後でリンクが成立した時点まで遅延させる。全文がアーカイブされているので、
今拾い損ねても後から拾い直せる——**取りこぼしは恒久的な損失にならない**。

### 原則3: LLMは「新規1単位の抽出」と「短い照合判定」だけ
LLMは有能だが確率的で、大量処理では非決定性がコストになる。
だからLLMの担当を最小化する: (a) 1配信/1か月ぶんのログからカードを抽出する、(b) 台帳ループと新カードの短いペアを判定する。
**蓄積・検索・集計・正規化はすべて決定的スクリプト**が行い、`grep` で追える平文（TSV/JSONL）に保つ。

## 3. データフロー（層とステージ）

```
        ┌─────────── 決定的スクリプト（LLMなし） ───────────┐   ┌── LLM ──┐   ┌─ 人間 ─┐
logs/ ─▶ S0 intake ─▶ raw/ ─▶ S1 normalize ─▶ normalized/ ─▶ S2 pack ─▶│抽出 ①│─▶ ingest/batch ─▶ cards/ + ledger/
                                                              S3 match ─▶│判定 ②│─▶ ingest ─▶ proposals
                                                              S4 packet ───────────────────▶│試聴/採否│─▶ S5 apply ─▶ handoff ─▶│起草 ③│─▶ Fandom貼付
                                                              doctor（独立）
```

層の役割:
- **raw層** (`data/raw/`): logsのバイト単位コピー＋`origin.json`（出所記録）。不変。
- **normalized層** (`data/normalized/`): 決定的変換の結果。ここで初めて辞書補正・文再結合・JST変換・シグナル検出が入る。
  - `sentences.tsv`: `t / mmss / url / asr(原文) / norm(補正後)`。**asrとnormを併存**させ、原文を失わない。
  - `chat.tsv`: チャット原文（補正しない）。
  - `signals.json`: 機械検出のヒント（後述）。
  - `meta.json`: タイトル・日付・件数・字幕形式・チャット源・配信関係など。
- **card層** (`data/cards/`, 通称 **Card Store**): 抽出された全カードの月別JSONL。ここがwikiの材料の本体。
- **ledger層** (`data/ledger/`): 伏線の台帳。`open`（未回収）/`closed`（回収済み）/`proposals`（クローズ提案）。
- **handoff層** (`data/handoff/`): 承認済み事項だけを、wikiスキルの受け渡し形式に整形したもの。

## 4. シグナル検出（S1）— 機能・名言の在り処を機械が指す

`signals.json` に4種のヒントを出す。いずれも**候補提示**であり、採否は下流のゲートで決まる。

1. **バースト**: 30秒ビンでチャットが急増した時刻。名言候補の在り処。
2. **字幕沈黙×チャット密集（ミスマッチ）**: チャットが密集しているのにASRが空白/ノイズの区間。
   **非言語音イベント（舌打ち・鳴き真似・笑い声・声質転換）の候補**。音声系の新機能はASRに写らないため、
   この「影」でしか機械検出できない。実例: 8-02の36:55〜37:24（カラスの鳴き真似〜いびき化、チャット爆発中に字幕29秒沈黙）。
3. **事後コメントの時刻**: 視聴者が付けた「4:34 震えた声可愛い」等のタイムスタンプ。無償のハイライト注釈。
4. **概要欄の新規行**: 前回まで無かった説明文の行。企画・ギミック告知（例「やる気ゲージ」。ASRには0回）。

機能検知はこの4種＋X告知突合の**5検知器アンサンブル**で、`config/features_registry.tsv`（既知機能）と突き合わせ、
未知なら capability カードとして浮かせる。初披露の主張は3段階で強度管理する:
コーパス内初観測（機械） < 初見驚愕型の反応（傍証） < 告知・明言の出典（これがある時だけ「初披露」と書く）。
出典が無いときの安全表現は「遅くとも◯月◯日の配信で確認できる」。

## 5. カードと台帳（中核データモデル）

**カード** = ログから抽出した1単位。6種（`SPEC.md` に完全定義）:
`event`（年表）/ `quote_candidate`（名言）/ `open_loop`（伏線）/ `capability`（機能）/ `profile_fact`（人物）/ `stream_note`（配信ギミック）。

**台帳（ledger）** = `open_loop` から生まれた「未回収の伏線」の一覧。7つの型:
目標宣言 / 願望 / 不能表明 / 予告・約束 / 過去参照 / 定型ネタ / 関係マーカー。
各ループは `expected_signal`（何が起きたら回収されるか）を持ち、これが将来の照合クエリになる。

**回収（クローズ）の流れ**: 新カード（event等）が既存ループの `expected_signal` を実現したとき、
S3が短いペアを作り→LLMが closed/related/unrelated を判定→closedは**提案**になり→人間が確認して確定（**ゲート4**）。
実例: 「ギャルボイスモデルも開発してください」(X 2026-02-28) の願望ループが、ギャル配信(2026-05-24)で回収成立。

## 6. 重要な設計判断（変更前に必ず読む）

### 6-1. 逐語ゲートの二段構え
S2 ingest（機械）が第一段: ASR由来は強制 `verbatim=false`、チャット/X由来は原文照合、OCRチャットは常に不可。
S5（人間）が第二段: 試聴して `逐語:` 行を書き、初めて `verbatim=true`。**機械は「疑わしきは false」に倒す**。

### 6-2. 照合の順序非依存（match_seen はペアID）
素朴には「照合済みカード」を記録して再照合を避けたくなるが、それだと
「閉じるカードを先に処理→その時ループ未開封→カードが照合済みになる→後でループが開いても二度と結びつかない」で回収を取りこぼす。
そこで `match_seen.json` は**照合済みペアID**（`loop_id__card_id`）を記録する。全カード×openループを毎回評価し、
既出ペアだけ除外する。結果、処理順に依存せず、過去ログをまとめて入れても同じ結果になる。
（因果制約 `card.date_jst > loop.opened` は保持。ループが開く前の出来事では閉じない。）

### 6-3. info.txt を信頼の起点にする
フォルダ名・ファイル名の命名は時期で揺れる（IDがフォルダ名に無い/ファイル名がタイトルのみ/Windows短縮形）。
だからS0は**`info.txt` の「動画ID」「投稿日」を正**とし、名前は補助に留める。両者が食い違えばinfo.txtを採り警告する。
これにより命名の移行途中でも、リネームを戻さずに取り込める。

### 6-4. 空ファイルでなく「既知の不在」を宣言する
コメントが無い配信は普通にある。空ファイルを作ると「取得済み0件」と「未取得」が区別できなくなる。
代わりに `config/known_absent.tsv` に理由付きで登録し、報告から消しつつ記録を残す。
欠落の重要度は種別で分ける: 字幕=ERROR / チャット・info=WARN / コメント=INFO。

### 6-5. アーカイブ再アップの日付分離
元ライブが破損し後日アーカイブとして別IDで再アップされると、投稿日と「出来事が起きた日」がずれる。
`config/stream_relations.tsv` に `archive_of` を宣言すると、カードの `date_jst` を元配信日へ補正し、
元の投稿日は `upload_date` に残す。これが無いと年表が再アップ日で誤る。

### 6-6. OCR復元チャットの隔離
チャットが保存できなかった配信は、映像からOCRで復元する（`*.live_chat_ocr.txt`）。
時刻は粗く（15秒グリッド）、誤字を含み、件数は下限値。よってバースト比較に注意し、**逐語には決して使わない**。
S2 ingestが機械的に `verbatim=false` に落とす。

### 6-7. LLM出力の形の揺れを取込口で正規化する
LLMは指示しても `evidence` を文字列配列でなく dict の配列（`[{"time":...,"text":...}]`）で返すことがある。
これを放置すると下流（照合・パケット）で連結時に落ちる。よって**取込口(S2 ingest)で `evidence`/`wiki_target` を必ず文字列リストへ正規化**し、
下流も `flat_text`/`as_str_list` で防御する。原則は「**外から来る形は信用せず、境界で正す**」。
既存データの一括修復は `repair_cards.py`。

## 7. gitに何を残すか

原則:「**決定的に再生成できるものは上げない。人間とLLMが作ったものは上げる**」。
raw/normalized/packs は再生成可（約80MB）で除外。llm_out/cards/ledger/review/handoff/state/config は再生成不可（約1MB）で保存。
これにより、クローンした人（or エージェント）は logs から S0→S1 を回すだけで作業を再開でき、
**wikiの1行 → カード → 出典URL → 元ログ**まで遡れる鎖が途切れない。実ルールは `.gitignore`。

## 8. 運転モード

- **モデルA（現行）**: 人間がステップごとに手動実行し、各出力を目視検証する。校正期に適する。
- **モデルB（将来）**: S0〜S4をエージェントが一括実行し、S5（試聴・採否・貼付）だけ人間に残す。`ROADMAP.md` 参照。
  スクリプトが標準ライブラリのみなのは、この移行を環境非依存にするため。

## 9. 既知の限界

- **usage-gated**: 音声系機能は使われた配信でしか観測できない。不使用と未実装をログから区別できない。
- **コラボ回の話者分離**: ASRは話者を区別しない。現コーパスはソロ配信のみで、コラボ対応は将来課題。
- **本体アカ偏重**: 現Xログはしずく本体アカのみ。年表の過去分はあき先生アカ・外部記事が出典で、別経路の収集が要る（`DATA-ISSUES.md §5`）。
- **Fandom非連携**: wikiソースの取得・書き込みは人間が行う（`web_fetch`が402）。自動投稿はしない。
