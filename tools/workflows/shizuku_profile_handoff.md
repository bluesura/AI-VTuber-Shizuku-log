- 記録日: 2026-09-10（JST）
- 対象: 2026-09-09〜2026-09-10のユーザーとの設計相談
- 状態: 要件整理・運用設計の段階。専用ツール、専用スキル、辞典本体は未実装。
- 今回の依頼: 「ここまでの状況を振り返り、AI用のファイルとして記録しといて」への対応。

## 1. 最初に把握すること

ユーザーは、AI VTuber「しずく」のログを配信ごとに読み進め、好きなもの、自己申告の属性、口癖、振る舞いなどを蓄積した、厚みのあるプロフィール・辞典を作りたい。

2023年と2026年の違いに加え、雑談・企画・演技・Xなどの文脈の違いを扱う。一度しか出なかった発言も保存し、繰り返し観測できた特徴には別途まとまった項目を用意する。

字幕の誤認識への対処もAIの分析工程に含める。ユーザーによるファイルの選択・添付・回答のコピー保存をなるべく減らし、「AIが1配信を分析して保存 → ユーザーが確認 → 判断を保存して次へ」という運用を望んでいる。

本書は実装済み機能の説明ではない。後述の配置、ファイル名、スキル名、分割幅は提案段階であり、存在や動作を確認せずに利用可能と説明しない。

## 2. ユーザーが明示した目的・希望

### 辞典に蓄積する内容

- 簡単な紹介文だけでなく、具体的な発言や好きなものなどを根拠とともに残す。
- 2023年のログから、当時しずくが自分について述べた傾向・属性を配信順に記録する。
- 過去の好みや特徴が2026年にも現れるか、注意深く確かめる。
- 2026年も配信を一つずつ分析し、変化を積み上げる。
- ユーザーは本質的な個性の連続性を感じている一方、AIの性能が変わり、話し方が大きく違う背景を挙げている。
- 雑談と企画では話し方が異なり、企画では演技に寄ることがある。文脈を考慮する。
- XにはXでのしずくのペルソナがある。YouTubeと無条件に混ぜない。

### 一度きりの発言と反復する特徴

ユーザーの明示的な希望:

> 一度きりの発言でも残したいと思います。ただ残し方に違いが出るかなと思います。1度の発言はその雑多な領域に残し、何度もでている発言はそういう領域にしっかり残すみたいな。

したがって、単発の発言を捨てたり、安定した特性と認定できる情報だけに抽出を絞ったりしない。

### 自動化とユーザーの役割

- 自動字幕には誤字があることを前提に、チャット・配信後コメント・概要欄から読みを補い、特徴を抽出する。
- 利用可能な文脈量・利用枠の範囲で、一つずつ分析・出力を進めたい。
- ユーザーが出力を確認し、その後はAIが次の対象へ進める運用を想定している。
- 今回までに依頼されたのは、設計の議論・説明と本書への記録。全量解析や実装の実行依頼はまだない。

## 4. 提案したデータの組み立て方

以下はユーザーの希望を受けてAIが提案した設計。詳細の確定・実装はこれから。

### 発言メモ

配信ごとの観測を広く保存する。単発、例外、矛盾する回答、企画だけの発言も対象とする。「この場面でこう答えた」と記録する。

最低限、観測ID、動画ID、配信日・公開日、時刻範囲、元ファイルと参照箇所、字幕原文、分析用の読み、前後のやり取り、分類、確認状態を持たせる案。

「食べ物」「ゲーム」「自己認識」「口調」などの緩い分類を付け、雑多な記録も後で検索できるようにする。

### 特徴辞典

反復する好み・口癖・反応などを項目別に整理し、根拠となる発言メモのIDを結び付ける。辞典にまとまった後も、元の発言メモを消したり移動して失ったりしない。

各項目には内容、観測された時期、媒体・場面、支持する観測、食い違う観測、判断の留保を残す。「2023年の雑談でよく見られた特徴」「Xでの特徴」など、範囲を限定した項目も認める。

反復回数だけで自動的に「確定」へ昇格させる閾値は決まっていない。基本プロフィールの事実確認も、反復回数とは分ける。

### 時期ごとのプロフィール

発言メモと特徴辞典から2023年・2026年のプロフィールを文章化する案。対象期間・処理済み範囲・観測時点を示し、未処理のログまで分析したように書かない。

## 5. 分析・比較について提案した原則

1. **自己申告と分析者の解釈を分ける。** 「優しい」と本人が述べたことと、対応から優しさを読み取ることは別の記録。
2. **内容と話し方を分ける。** 好み・自己定義と、語尾・一人称・冗談の表現方法を混同しない。
3. **文脈は場面ごとに付ける。** 配信タイトルの「雑談」「企画」だけで全発言を分類しない。質問への回答、言わせる指示、引用・歌詞・朗読、演技などを区別する。
4. **話者を分ける。** 視聴者の発言や開発者の説明を、しずくの自己申告に変換しない。Xの本文と引用先も分ける。
5. **独立した反復を確認する。** 同じ配信内の連呼、字幕の重複、分割境界、切り抜き・再アップを別々の反復証拠に数えない。同じ語句だけでなく、意味や対応の傾向の反復も検討する。
6. **言及の不在を消失としない。** 未調査、話題が出なかった、同じ話題に違う回答をした、明示的に否定した、を区別する。
7. **2026年の新しい観測を先に抽出する。** その後で2023年や既存辞典と照合する。過去の特徴だけを探し、新しい特徴を取りこぼす流れを避ける。
8. **連続性は具体的な根拠で記述する。** ユーザーの「本質的な個性が残っている」という感覚を出発点にしつつ、共通点を必ず見つけることを分析の結論として固定しない。
9. **変化と原因の仮説を分ける。** 話し方の変化が、モデル性能・設定・企画・相手などのどれに由来するかは、ログだけでは断定できないことがある。
10. **音声にしか現れない特徴を字幕から断定しない。** 発音・抑揚・声質などには別途音声の確認が必要。

「発言したことの確認」「特性としての反復・定着」「ユーザーの採用判断」は別の軸として扱う。一度きりでも発言を確認できることはあり、繰り返されていても演技に限られることがある。

## 6. 自動字幕と補正の扱い

### 入力のまとめ方

- 単位は1字幕ファイルではなく、同じ動画IDの資料一式。
- 主な字幕は `.ja.srt` / `.ja.sbv.txt`。同じ字幕の形式違いなら主に読む方を一つ選び、二重計上しない。
- 実際には `.ja.srt.txt` などの揺れもある。チャット・コメントの主な実ファイル名は `.live_chat.txt` / `.comments.txt`。ユーザーは説明で `.livechat.txt` / `.comment.txt` とも表記している。
- `.info.txt` は企画・名称・出演者・動画IDなどの確認に使う。投稿日と実際の配信日が同じとは限らない。
- チャットは質問や指示を確認するために使う。時刻が近いだけで応答関係を決めない。OCR由来か、欠落や時刻の粗さがあるかも記録する。
- 配信後コメントは聞き取りや該当時刻を探す手掛かり。視聴者の解釈を本人の発言に置き換えない。

### 原文・読み・根拠を併存させる

`logs/` の一次資料は上書きせず、分析用の読みと補正記録を別に保存する案。

| 状態 | 対応 |
| --- | --- |
| 根拠の明確な表記補正 | 分析用の読みへ反映し、原文・根拠・参照位置を残す |
| 候補はあるが断定できない | 読みの候補と不確かさを残す |
| 対象名、肯定・否定、話者などが不明 | 発言メモには残すが、その不明部分に依存する特徴の採用は保留する |

例として「秋先生」を周辺資料から「あき先生」と読む場合も、文脈補正と音声確認を区別する。すべての「秋」を一括置換するような辞書にしない。

全字幕の完全な校正を先行条件にせず、全文を順に読みながら、特徴の抽出に関わる箇所を重点的に補正・記録する案を説明した。全文校正済みとは表示しない。

既存の `s1_normalize.py` は `asr` と `norm` を別列に保存する。一方、`s2_pack.py` が分析に渡す字幕は主に `norm`。今回の用途では、必要な原文と補正根拠もAI・レビュアーが参照できる形を検討する。

## 7. 提案した自動処理・レビュー・再開フロー

1. 進捗から未処理の配信を日付順に選ぶ。
2. 同じ動画IDの字幕、チャット、コメント、概要欄を集め、入力の欠落・形式・出所を確認する。
3. 長時間のものは区間に分け、順番に読む。補正案と発言メモを区間ごとに保存する。
4. 全区間が揃ったことを検証し、重複を整理する。
5. 配信全体と既存の観測を照合し、特徴辞典の更新案を作る。
6. 確認用レポートを保存してユーザーに表示し、確認待ちにする。
7. ユーザーの採用・修正・保留を記録し、採用分を辞典へ反映する。
8. 「次へ」という指示を含む返答に従って次の配信へ進む。

### 読み飛ばしと長時間配信への対処

- キーワード一致部分やハイライトだけの分析にしない。単発の小さな発言を拾うため、対象字幕の全区間を順に処理する。
- 初期案は10〜20分程度を目安とし、発言密度で調整する。固定の最適値やモデルの上限ではなく、試行して決める値。
- 会話の切れ目を考慮し、境界に前後の文脈を付ける。持続中の企画・役柄・語尾指示も引き継ぐ。
- 入力だけでなく出力・会話履歴・照合資料の余地も確保する。
- 読み終えた区間を記録し、分割部分の欠落や重複を検証する。分析対象がない区間も、処理済みであることを残す。

### レビューの操作イメージ（未実装）

ユーザーが主に読むのは、配信ごとのMarkdownレポート。発言メモ、新規・補強・矛盾の提案、補正前後、要確認事項、該当時刻へのリンク、分析済み範囲を表示する案。

返答例:

> O-007は保留。O-012は企画中の発言として扱って。残りは採用して次へ。

問題がなければ「採用して次へ」で済むようにする。手動でJSONを編集したり、回答をコピーして保存したりすることは通常の操作にしない。

保留項目を残したまま次の配信へ進めるようにする。「レポートを採用」と「音声を試聴して逐語確認」は別に記録し、前者だけで字幕を逐語確認済みにしない。

### 中断・再開

- 1配信の完了まで保存を遅らせず、区間ごとに結果を保存する。
- 動画ID、処理済み区間、確認待ち事項、入力ファイルの識別情報、手順・プロンプトの版を進捗に残す案。
- 全区間の保存と検証が完了するまで、その配信を分析完了・確認待ちにしない。
- 同じ対象を再開しても観測やレビューを二重登録しない設計にする。
- 会話の記憶だけに依存せず、別の会話でも保存済み状態から再開できるようにする。
- 文脈量とアカウントの利用枠を区別する。上限直前の確実な保存や、処理できる配信本数を保証しない。上限回復後に勝手に再起動する仕組みは未設計。
