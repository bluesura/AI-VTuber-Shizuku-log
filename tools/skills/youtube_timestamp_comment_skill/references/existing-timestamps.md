# 既存目次の確認・手動投稿・コメントの再収録

対象動画のコメント確認から、ユーザーの手動投稿後の公開確認までを扱う。YouTubeとFandomの一覧照合やWiki編集は別スキルの作業であり、実行の前提にしない。

## 目次の充実度を判断する

通常コメントの本文を読む。ライブチャットの時刻、コメント投稿日時、ファイルヘッダーは既存目次として数えない。`03:22`、`[03:22]`、`1:00:25` や同じ動画の時刻付きリンクが候補となる。ハッシュタグの有無は条件にしない。

| 確認できた内容 | 判断と次の操作 |
|---|---|
| 主要な話題を広く案内する目次 | 十分。生成を省略する |
| 単発の時刻・一部の見どころのみ | 部分的。再取得してから不足範囲を検討する |
| 歌枠の曲目一覧 | 曲探しには十分。雑談等の案内も必要か、配信内容と依頼の範囲から判断する |
| 概要欄に公式チャプター | コメントとは区別して記録し、同じ案内の重複を避ける。章が粗い場合は不足を説明する |
| 目次がない | 再取得してから生成の要否を判断する |
| 取得失敗・不完全・判断不能 | 保留。目次なしと確定しない |

項目数や最初と最後の時刻だけで充実度を確定しない。複数コメントで十分に案内されている場合もある。既存本文、infoの内容・公式チャプター、必要に応じて字幕の話題構成を比べる。詳しい目次がなくても、短い配信や単一の内容なら少ない項目で十分な場合がある。

不足すると判断したら、理由（例：曲目は揃っているが長い雑談部分が未収録）と作成範囲を示す。補足で足りる場合は補足を優先し、全体の目次が必要なら全体案とする。他人のコメントを改変したり、その人が書いたように案を扱ったりしない。

## リポジトリの補助コマンド

ルートから実行する。補助スクリプトはリポジトリ側の `tools/scripts/` にあり、配布パッケージには含まれない。

```powershell
# 保存済みコメントだけを確認する
python tools/scripts/check_youtube_timestamps.py <動画ID> --check-only

# 不足・未収録の場合、または手動投稿後に、公開コメントを再取得する
python tools/scripts/check_youtube_timestamps.py <動画ID> --refresh
```

複数IDを指定できる。このツールは時刻の検出とコメントの収集を担当し、**目次の充実度や投稿状態は判定しない**。JSONの `generate` は従来の「時刻があるか」に基づく補助値であり、本スキルの最終判断に直結させない。

| ツールの結果 | スキル側で行う判断 |
|---|---|
| `existing_local` / `existing_after_refresh` | 本文を読んで充実度を確認。不足なら `--refresh` 後に再判定する |
| `needs_generation` | 再取得では時刻なし。公式チャプターと投稿待ち記録も確認して作成を判断する |
| `refresh_required` | ローカルだけでは不足。再取得してから判断する |
| `refresh_failed` | 保留。生成へ進まない |

引数なしの既定動作は、ローカルに時刻があれば再取得を省略する。したがって「時刻はあるが目次が不足する」場合も、明示的に `--refresh` を使う。

通常コメントだけを既存の匿名化・書式で更新し、字幕・ASR・ライブチャット・動画情報は更新しない。旧コメントは `outputs/youtube-timestamps/comment-refresh/` へ退避し、取得失敗・競合時は上書きしない。匿名化前の著者情報や対応表を保存しない。

補助スクリプトがない環境では、利用可能な公開コメント取得手段で同じ判断順を守る。取得できない場合は確認不可とする。

## 手動投稿を挟む進捗

このリポジトリでは、実際に案を作成した動画の進捗をGit管理外の `outputs/youtube-timestamps/status/<動画ID>.json` に記録する。一般の環境では同等の作業記録を使う。これは生成物・確認記録であり、収集済みコメントではない。目次の完成本文はチャットに返す。

最低限、動画ID、状態、更新日時（タイムゾーン付き）、チャットに提示した本文のSHA-256、既存目次の評価と不足理由、公開確認の結果・確認日時を残す。投稿日時が分かれば `posted_at`、次に取得できる日時を `check_after` として残す。本文ハッシュは提示したコードブロック内の本文をLFへ統一し、末尾改行を除いてUTF-8で計算する。認証情報や視聴者の表示名は含めない。既存記録を読み、別の案を暗黙に上書きしない。

| 状態 | 意味と次の操作 |
|---|---|
| `awaiting_manual_post` | 案を提示済み。ユーザーの投稿を待つ。同じ案を新規生成しない |
| `posted_unverified` | ユーザーから投稿済みとの連絡あり。再取得して今回の本文を探す |
| `verified` | 今回の本文を公開取得し、匿名化したコメントファイルへ保存できた |
| `check_blocked` | 取得失敗等で判断できない。前の投稿状態も保持し、確認だけを再開する |

案を再表示する場合は、既存のチャット出力を案内する。本文を参照できなければ、新しく再投稿用の案を作る前に確認する。ユーザーが編集・取り下げを指定したときだけ、その内容に合わせて記録を更新する。

ユーザーの「投稿した」という連絡で `posted_unverified` に進める。**投稿から最低限2〜3分待ってから取得する。この運用では3分を基準にする。** 正確な投稿時刻が不明なら、投稿済みの連絡を受けた時刻から3分空ける。投稿直後の取得結果を根拠に非表示と判断しない。待機が必要なら、短い待機に分けるか `check_after` を伝えて確認待ちで止める。後者を自動予約したと誤解させない。

投稿後の再取得では、他の既存タイムスタンプが見つかっただけで `verified` にしない。今回の本文に特有の見出しと時刻・順序などを照合する。改行等の表示差は許容できるが、曖昧なら公開未確認を維持する。ユーザーが本文を編集した場合は編集内容を踏まえて照合する。`verified` は確認日時点の観測であり、恒久的な公開を保証しない。後日見つからなくなったら、過去の確認記録を残して現在の状態を `posted_unverified` に戻す。

## ユーザー提供リストとの照合と既存本文の改稿

ユーザーのURL一覧・本文は、ユーザー提供資料として収集済み公開コメントと区別する。シークレットウィンドウ等での見え方の報告も、そのままスパム判定の確定根拠にしない。動画IDで照合し、提供本文あり／なし、現在の公開取得結果、単発の時刻／全体目次、次の対応を作業一覧へ記録する。

- リスト外で目次不足が新たに見つかった場合は一覧へ追加し、作成に進む前にユーザーへ確認する。既存コメントの正常な再取得と匿名化したログの更新は、その依頼の範囲で進める。
- リスト内で本文がない動画は、収録済みの一次ログを探し、不足するログだけを別の収集手順で補って作成する。既存ログを無条件に全件取り直さない。
- 本文が提供されている動画は、それを起点に見出し・時刻を元ログへ照合し、配信固有の言い回しや流れを保って改稿する。不要な長文、過剰な煽り、直接的で文脈を欠く表現、ネタバレ、誤認識を整理する。特定の単語がスパム原因だったと断定しない。
- 提案は1動画ずつ、主な変更理由とコピー可能な本文を提示する。別動画の案をまとめて大量に出したり、改稿のために再投稿を自動で促したりしない。
- 既存本文の改善依頼が明示されている場合は、投稿待ち・公開未確認でもその案の改稿を行える。旧案との関係を記録し、新規の別投稿を作った扱いにしない。

## 公開未確認・スパム判定への対応

YouTubeはコメントを自動判定し、確認のために保留することがある（[公式ヘルプ](https://support.google.com/youtube/answer/9482362?hl=ja)）。ただし、公開取得できないという結果だけでスパム・保留・削除の原因は断定しない。

- 投稿直後の確認で取得できなくても、今回の本文を捏造して `comments.txt` へ追記しない。
- 「投稿済み・公開未確認」と報告して止める。短時間の再取得ループや再投稿の催促を行わない。非表示だけを理由に自動で文面変更・分割投稿をしない。ユーザーが改稿を依頼した場合は上記の手順で文章を見直し、公開を保証しない。
- 時間を置いた再確認またはユーザーからの依頼で、公開確認を再開する。常駐監視・予約処理は自動で作らない。
- 「特定の文字数・ハッシュタグなら必ず公開される」等の保証をしない。公開の可否と目次本文の品質は分けて報告する。

完了時は、動画IDごとに既存目次の評価、生成／省略／保留、投稿待ちか公開確認済みか、コメントファイルの更新結果を簡潔に示す。
