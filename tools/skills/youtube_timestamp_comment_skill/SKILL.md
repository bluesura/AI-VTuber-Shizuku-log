# YouTube配信ログ → コメント用タイムスタンプ生成

## 目的

YouTube からダウンロードした 4 種類の生ファイルを直接読み込み、YouTube コメント欄に貼付可能なタイムスタンプ付きシーン説明を生成する。

単なる事務的な事象の羅列（議事録）ではなく、配信の熱量や文脈（Vibe）が伝わる魅力的な目次を作る。特に **「要約」ではなく「予告（Teaser）」** として機能させ、視聴者が「何があったのか」気になって思わずタイムスタンプをクリックしたくなるよう誘導することが最大の目的である。

生成した目次本文は**チャットに直接**返し、投稿用の完成ファイルは作らない。前処理ファイルと投稿確認の進捗は、一次ログと分けた作業領域へ保存できる。

## 対象と他スキルとの境界

このスキルは、指定された動画ID・URLまたは提供されたログを起点にする。YouTubeの最新アーカイブとFandomの「動画・配信」の照合、対象動画の選定、未収録の配信ログ収集、Wikiの編集は別の作業として扱い、このスキルの必須手順や実行権限に含めない。照合が必要なら別のログ収集・Wiki編集ワークフローを案内し、その結果から動画IDとログの所在を受け取る。Fandom未掲載の動画にも、対象の指定とログがあれば単独で使える。

このスキル内で行う再取得は、対象動画の通常コメントの更新。字幕補完やASRが必要なら、別の収集・文字起こし手順へ引き継ぐ。YouTubeへのコメント投稿・編集・削除はユーザーが手動で行い、エージェントは行わない。

## 配信者の扱い

メイン配信者は基本的に**「しずく」**として扱ってよい。ただしイベント回などで配信者が入れ替わる可能性があるため、次を確認してから書き始める。

- info ファイルのタイトル・概要欄、sbv ファイル冒頭の自己紹介に別名義が出ていないか
- ユーザーが配信者名を明示している場合は、そちらを最優先で採用する

以降の記述で「しずく」とあるのは「その回のメイン配信者」と読み替えること。

## 作成前に既存目次の充実度を確認する【最優先】

字幕の前処理や目次の生成より先に、対象動画の保存済み `comments` を確認する。

1. 作業記録に「投稿待ち」「投稿済み・公開未確認」があれば、新しい案を重ねて作らず、続きの確認を行う。
2. 保存済みコメントの本文を読み、配信の主要な話題を広く案内できる目次があれば生成を省略する。単発の時刻や少数の見どころだけで、十分な目次とは判断しない。件数だけで合否を決めず、概要欄の公式チャプターも含めて不足する範囲を見る。投稿日時やファイルヘッダーは動画内時刻として数えない。
3. 目次がない・不足する・ファイルがない場合は、YouTubeの公開通常コメントを再取得する。匿名化して対象動画の `comments.txt` だけを更新し、充実度を再判定する。取得失敗・不完全・コメント非公開なら「存在しない」とみなさず保留する。
4. 正常な再取得後にも全体の案内が不足する動画だけ、字幕・チャットから作成する。既存の曲目一覧などで足りる用途は尊重し、追加する範囲と理由を示す。十分な目次があるか判断できなければ、短い既存確認結果を示して保留する。
5. ユーザーが投稿したら、投稿から最低限2〜3分（この運用では3分）待ってから、既存目次がある動画でもコメントを再取得し、今回投稿された本文の公開確認を行う。投稿直後に取得した結果で非表示と判断しない。見つからない場合は「投稿済み・公開未確認」を維持する。反映後に見えなくなる場合もあるため、公開確認には確認日時を残す。

既存確認で終了する動画には、以下のSBV必須・前処理の条件を適用しない。詳細とリポジトリ内の確認コマンドは [既存タイムスタンプの確認](references/existing-timestamps.md) を参照。

タイムスタンプとハッシュタグは別のもの。`#` の有無は目次の充実度の判定条件にしない。新規目次の生成結果をYouTubeから取得したコメントとして `comments.txt` に混ぜない。生成案を提示してユーザーの手動投稿を待ち、投稿後に公開取得できた内容だけを一次ログへ収録する。進捗とスパム判定への対応も [既存タイムスタンプの確認](references/existing-timestamps.md) に従う。

ユーザーが既存本文・確認済みURL一覧を提示した場合は、同参考資料の「ユーザー提供リストとの照合と既存本文の改稿」も読む。リスト外の新規候補は先に確認し、既存本文の調整案は依頼された順に1件ずつ提示する。

## 入力ファイルの特定

通常は `/mnt/user-data/uploads/` に置かれている。**ファイル名は配信ごとに揺れる**（`◯◯_ja_sbv.txt` / `◯◯.sbv.txt` / `◯◯_live_chat.txt` など）ため、**拡張子の完全一致で探してはいけない。ファイル名に含まれるキーワードで判定する。**

| 種別 | 判定キーワード（ファイル名に含まれる） | 必須 |
|------|--------------------------------|------|
| ① 動画メタ情報 | `info` | 推奨 |
| ② 字幕・発言ログ | `sbv` | **必須** |
| ③ ライブチャット | `live_chat`（かつ `ocr` を**含まない**） | 推奨 |
| ③-B ライブチャット（OCR復元） | `live_chat_ocr` / `ocr` | ③が無い場合の代替 |
| ④ 投稿後コメント | `comments` | 既存目次の充実度を判定。不足・未収録なら先に再取得 |

- **`.srt` ファイルは無視する。** sbv ファイルと内容が重複するうえ、行分割・番号付けが異なり照合を誤る原因になる。
- glob は `*sbv*.txt` / `*live_chat*.txt` / `*info*.txt` / `*comments*.txt` の形で書く
- **`*live_chat*.txt` は `*live_chat_ocr*.txt` にもマッチする。** ③と③-Bは信頼度がまったく異なるため、ファイル名に `ocr` を含むかで**必ず振り分ける**（前処理スクリプトで実施済み）
- **③と③-Bが両方ある場合は③（通常版）だけを使い、OCR版は無視する。** 同一コメントの二重計上を防ぐため
- ③-Bのみの場合は「**OCRモード**」となる。フォーマットと制約は下記 ③-B を必ず読んでから作業する
- 欠けているファイルがある場合は、その旨を伝えたうえで揃っているファイルだけで進めてよい
- ただし **sbv ファイルは必須**。無い場合、またはパースに失敗した場合は、ハルシネーション防止のため作業を止めてユーザーに確認する

## 各ファイルのフォーマット

### ① info ファイル（動画メタ情報）

```
# 動画情報
タイトル  : （動画タイトル）
投稿日    : YYYY-MM-DD
動画ID    : （ID文字列）
URL       : https://www.youtube.com/watch?v=（ID）

────────
【説明】
────────
（概要欄テキスト）
```

読み取るべき情報:

- 配信タイトル・投稿日（出力ヘッダーへの参照用）
- 概要欄に `@` `#` コマンドの説明がある場合、クイズ・ゲームなど進行管理のあるイベント配信の可能性が高い。その場合は `references/command-driven-chat.md` を参照する（通常配信では登場しないため、無ければ読まなくてよい）
- 概要欄に書かれた企画・コーナー名（構成の予告になっていることが多い）

### ② sbv ファイル（字幕・発言ログ）

**SBV 標準形式**。1 エントリは「開始時刻,終了時刻」の行 → 次の行が発言内容、の 2 行構成。エントリ間は空行で区切られる。

```
0:03:11.400,0:03:20.910
こんにちは。

0:03:44.920,0:03:47.760
配信の[音楽]感想はシャープしずく実験

0:05:09.740,0:05:15.829
[音楽]
```

- 時刻は `H:MM:SS.mmm`。**カンマ区切りで開始・終了が並ぶ**（`[H:MM:SS]` のような角括弧形式ではない）
- 使用するのは**開始時刻のみ**
- 改行コードが CRLF（`\r\n`）のことがあるので `\r` を除去してからパースする
- `[音楽]` / `🎵 [音楽]` は BGM 区間。発言テキストの途中に `[音楽]` が挿入されることも多い
- これは**配信者の発言のみ**を記録したもの
- **1 エントリは 2〜4 秒程度で、文の途中でぶつ切りにされる。** 1 エントリだけ読んでも意味が取れないので、必ず前後を連結して読む（後述の集約タイムラインを使う）
- live_chat ファイルの `[M:SS]` と表記単位が異なる。相互参照時は秒数に揃えて照合する（sbv の `0:04:43` = チャットの `[4:43]`）

### ③ live_chat ファイル（ライブチャットログ）

```
# ライブチャット一覧
# 動画: （タイトル）
# URL : （URL）
# 件数: （件数）

[-M:SS] @ユーザー名: コメント内容   ← 配信開始前（負の時刻）
[M:SS] @ユーザー名: コメント内容    ← 配信中（正の時刻）
```

- タイムスタンプ形式は `[M:SS]`。60分を超える場合は `[H:MM:SS]` になることもある
- 負のタイムスタンプは配信開始前の待機中コメント
- 各行は `[タイムスタンプ] @ユーザー名: メッセージ`
- チャットのユーザー名は出力に一切含めない

**`@` `#` コマンドは基本的に登場しない。** 雑談配信・ASMR・歌枠などの通常配信では、コメント本文の先頭記号を気にせず、すべて通常の視聴者反応（sbv の該当発言の裏取り・チャット反応スパイクの材料）として扱ってよい。

コメント本文が `@` `#` で始まる行が見られる、または info ファイルの概要欄にコマンドの説明がある場合は、クイズ・ゲームなど進行管理のあるイベント配信の可能性がある。その場合のみ `references/command-driven-chat.md` を読み、コメント種別の判別・運営アカウントの見分け方・0件だった場合の扱いに従う。

---

### ③-B live_chat_ocr ファイル（OCR復元ライブチャット）

配信のチャットリプレイが保存されなかった回で、**録画映像のチャット欄を画像から文字起こしして復元したもの**。行の見た目は ③ とほぼ同じだが、**中身の信頼度がまったく違う**ため、③ と同じつもりで扱ってはいけない。

```
[0:00:00] @myon_kichi: 待機！
[0:00:00] @きよ: こんにちは
[0:00:15] @参謀長: パンポー！
[0:00:15] @DEEPBLUE2633: パンパカパンパカポー
[0:00:30] @あおおい文月: おーすごい画面だ
```

フォーマット上の違い:

- タイムスタンプは `[H:MM:SS]` 表記。**キャプチャ間隔（例では15秒）に丸められた概算値**で、同一時刻に多数のコメントが並ぶ
- ヘッダー行（`# ライブチャット一覧` など）は無いことがある
- 配信開始前のコメントも**負の時刻にならず `[0:00:00]` に潰れている**ことが多い（`待機` `パンパカ〜` が冒頭に大量に溜まる）
- 同一バケット内のコメントの並びは、元の投稿順を保っているとは限らない

**扱ううえでの制約（すべて重要）:**

| 制約 | 意味すること |
|------|------------|
| **時刻が粗い** | チャット時刻は「その時刻までに投稿された」という上限値。実際の投稿は**それより前**。反応の遅れも加わるので、きっかけになった発言は sbv 側でさらに数十秒前にある |
| **網羅していない** | 画面に写った分しか拾えない。流速が速い場面ほど取りこぼす。**「コメントが少ない＝盛り上がっていない」ではない** |
| **件数が頭打ちになる** | 1画面に表示される行数が上限になるため、大盛り上がりの区間ほど件数が実数より圧縮される。件数の多寡より**リアクション語の中身**で判断する |
| **重複が混ざる** | 同じコメントが画面に残り続け、複数フレームで拾われる。前処理スクリプトで90秒以内の同一コメントを畳んでいる |
| **文字が化ける** | 視覚的に似た文字に誤読される（ロ/口、カ/力、エ/工、ー/一、ｗ/w など）。絵文字・スタンプは欠落しがち |
| **先頭記号が落ちる** | `@` `#` コマンドの記号がOCRで脱落・誤読されることがある。**0件でも「コマンド未使用の配信」と断定しない**（info の概要欄を必ず確認する） |

**したがって、OCRモードでは:**

- 出力するタイムスタンプの時刻は、**例外なく sbv 側で確定する**。チャットの時刻をそのまま出力に写さない
- チャットは「その辺りでこういう空気だった」という**傍証**としてのみ使う。ルール9（sbv 起点の原則）は通常時より厳格に適用する
- 固有名詞の裏取りには使わない（後述ルール2-6）

---

### ④ comments ファイル（投稿後コメント）

```
# コメント一覧
# 動画: （タイトル）
# URL : （URL）
# 件数: （件数）

[YYYY-MM-DD HH:MM UTC] @ユーザー名（👍 N）
コメント内容
```

- 動画投稿後の通常コメント。時刻は動画内時刻ではなく投稿日時なので、シーンの時刻とは対応しない
- 視聴後の感想・評価として参照する
- 既存目次の確認は件数にかかわらず行う。その確認後、感想から見どころを拾う用途では、件数が少ない場合や罵倒・スパム系のみの場合は参照を省略してよい

## 前処理

新規生成が必要と判定された動画では、規模にかかわらず、**必ず次のスクリプトを実行してから読み始める**。sbv は 1 エントリ 2〜4 秒でぶつ切りにされているため、生のまま読むと文脈が繋がらず、時刻照合もずれてハルシネーションの原因になる。

スクリプトを `/tmp/build_timeline.py` に保存して実行する。

```python
import re, sys, glob, os
from collections import Counter

BASE = sys.argv[1] if len(sys.argv) > 1 else "/mnt/user-data/uploads"

# 盛り上がりの指標になる語
REACT = ["草","ｗ","笑","泣","エモ","すご","ヤバ","やば","マジ","まじ","神","かわい","かわよ",
         "!?","！？","？？","88","おめ","天才","尊い","惜し","正解","不正解","www",
         "たすかる","助かる","へぇ","ひゅー","ヒュー","えぇ"]
# 挨拶・定型句はシーンとしては無価値なのでスパイク検出から除外する
NOISE = ["待機","おつしず","パンパカ","ぱんぱか","お疲れ","おつかれ","こんばんは","こんにちは",
         "こんちわ","おはよう","初見","乙"]
# コーナーの切れ目を示す配信者の定型句
CORNER = ["コメントで教えて","コメントで自慢","コメントしてください","ここで1つ",
          "ではこう聞きましょう","質問です","コーナー","でいきますよ","1つに絞る",
          "お知らせ","次は","いってみましょう"]

def to_sec(ts):
    neg = ts.startswith("-"); s = 0
    for p in ts.lstrip("-").split(":"): s = s * 60 + int(float(p))
    return -s if neg else s

def fmt(sec):
    h, r = divmod(abs(sec), 3600); m, s = divmod(r, 60)
    sign = "-" if sec < 0 else ""
    return f"{sign}{h}:{m:02d}:{s:02d}" if h else f"{sign}{m}:{s:02d}"

# ---- sbv（SBV標準形式: 開始,終了 → 次行が本文）----
sbv = []
for path in glob.glob(f"{BASE}/*sbv*.txt"):
    lines = open(path, encoding="utf-8", errors="replace").read().replace("\r", "").splitlines()
    for i, line in enumerate(lines):
        m = re.fullmatch(r"(\d+(?::\d{2})+(?:\.\d+)?),(\d+(?::\d{2})+(?:\.\d+)?)", line.strip())
        if m and i + 1 < len(lines) and lines[i + 1].strip():
            sbv.append((to_sec(m.group(1)), lines[i + 1].strip()))
sbv.sort(key=lambda x: x[0])

# ---- live_chat（通常版 / OCR復元版）----
# glob `*live_chat*.txt` は `*live_chat_ocr*.txt` にもマッチするため、必ず振り分ける
cand = sorted(set(glob.glob(f"{BASE}/*live_chat*.txt")) | set(glob.glob(f"{BASE}/*chat*ocr*.txt")))
ocr_paths = [p for p in cand if "ocr" in os.path.basename(p).lower()]
raw_paths = [p for p in cand if p not in ocr_paths]
use_paths = raw_paths or ocr_paths          # 通常版があればそちらを優先（二重計上の防止）
OCR = bool(ocr_paths) and not raw_paths     # OCRモード判定

chat, unparsed = [], 0
for path in use_paths:
    for line in open(path, encoding="utf-8", errors="replace"):
        line = line.replace("\r", "").rstrip("\n")
        if not line.strip() or line.lstrip().startswith("#"): continue   # ヘッダ行
        m = re.match(r"\s*\[(-?\d+(?::\d{2})+)\]\s*@?\s*(.+?)\s*[:：]\s*(.*)", line)
        if m: chat.append((to_sec(m.group(1)), "@" + m.group(2), m.group(3).strip()))
        else: unparsed += 1
chat.sort(key=lambda x: x[0])   # 同時刻は元ファイルの並び順を維持（OCRは同一バケットに多数入る）

# ---- OCR: 連続フレームで重複取得された同一コメントを畳む ----
raw_ts = sorted({t for t, _, _ in chat})   # 刻み幅の推定は重複除去前の時刻集合で行う
dup = 0
if OCR and chat:
    seen, ded = {}, []
    for t, u, c in chat:
        k = (u, c)
        if k in seen and t - seen[k] <= 90:
            seen[k] = t; dup += 1; continue     # 同じコメントが画面に残り続けたもの
        seen[k] = t; ded.append((t, u, c))
    chat = ded

# ---- 検証: ここで止まったら先に進まない ----
assert sbv, "sbv のパースに失敗（0件）。ファイル名・フォーマットを確認し、作業を止めてユーザーに確認する"
print(f"== 読み込み結果 ==\n  sbv: {len(sbv)}件 / 最終 {fmt(sbv[-1][0])}\n  chat: {len(chat)}件"
      + (f" (重複除去 {dup}件)" if dup else "") + (f" / 未パース {unparsed}行" if unparsed else ""))
if raw_paths and ocr_paths:
    print("  !! 通常版とOCR版の live_chat が両方あるため、通常版のみを使用した")

# ---- OCRモードの精度パラメータ ----
if OCR:
    step = Counter(b - a for a, b in zip(raw_ts, raw_ts[1:])).most_common(1)
    gran = step[0][0] if step else 0
    print(f"\n== !! OCR復元チャットモード（タイムスタンプ刻み: 約{gran}秒） !!\n"
          f"  - チャット時刻は丸め済みの概算。出力の時刻は必ず sbv 側で確定すること\n"
          f"  - 画面に写った分しか拾えないため件数は実際より少なく、上限で頭打ちになる\n"
          f"  - OCR誤読があるため、チャット文字列を固有名詞の裏取りに使わない")
    PAD_B, PAD_A, BUCKET, W = 20, 60, 60, 30
else:
    PAD_B, PAD_A, BUCKET, W = 15, 30, 30, 20

# ---- 1) 精密タイムライン（最終的な時刻確定用。grepして使う）----
with open("/tmp/timeline.txt", "w", encoding="utf-8") as f:
    for t, text in sbv:
        near = [c for ct, _, c in chat if t - PAD_B <= ct <= t + PAD_A]
        f.write(f"[{fmt(t)}] SBV: {text}\n")
        for c in near[:6]: f.write(f"          chat: {c}\n")

# ---- 2) 集約タイムライン（通読用。本文を連結）----
with open("/tmp/condensed.txt", "w", encoding="utf-8") as f:
    t, end = 0, sbv[-1][0] + W
    while t < end:
        txt = "".join(x for s, x in sbv if t <= s < t + W)
        cs = [c for ct, _, c in chat if t <= ct < t + W]
        if txt.strip() or cs:
            f.write(f"[{fmt(t)}] {txt}\n")
            if cs: f.write("   >> " + " / ".join(cs[:10]) + "\n")
        t += W

# ---- 3) 運営候補（# コメントを多く投稿しているアカウント）----
hashers = Counter(u for _, u, c in chat if c.startswith("#"))
print("\n== # コメント投稿数（上位＝運営候補。名前は内部判断のみに使う） ==")
if not hashers:
    print("  なし（コマンド未使用の配信。sbv発言のみを起点にする）"
          + ("／OCRでは先頭記号が脱落することがあるため、info の概要欄にコマンド説明があれば0件と断定しない" if OCR else ""))
for u, n in hashers.most_common(5): print(f"  {u}: {n}")

top = hashers.most_common(1)[0][0] if hashers else None
if top:
    print("\n== 運営 # コメント（進行の節目） ==")
    for t, u, c in chat:
        if u == top and c.startswith("#"): print(f"  [{fmt(t)}] {c}")

# ---- 4) コーナー検出（配信者の定型句から構成を割り出す）----
print("\n== コーナーの切れ目候補 ==")
for t, text in sbv:
    if any(k in text for k in CORNER): print(f"  [{fmt(t)}] {text[:45]}")

# ---- 5) チャットが沸いた区間 上位30（＝ハイライト候補）----
buckets = {}
for t, _, c in chat:
    if t < 0 or any(k in c for k in NOISE): continue
    b = t // BUCKET
    hit = sum(1 for k in REACT if k in c)
    d = buckets.setdefault(b, [0, 0]); d[0] += 1; d[1] += hit
hot = sorted(buckets.items(), key=lambda kv: (-kv[1][1], -kv[1][0]))[:30]
print(f"\n== チャット反応スパイク（{BUCKET}秒単位 / 件数 / リアクション語数 / 直前のSBV発言） ==")
if OCR: print("  ※件数は画面写り込み分のみ。件数の多寡ではなくリアクション語の中身で判断する")
for b, (n, r) in sorted(hot):
    t = b * BUCKET
    prev = [s for s in sbv if s[0] <= t + BUCKET]
    line = prev[-1][1][:40] if prev else "(SBV該当なし)"
    print(f"  [{fmt(t)}] chat={n} react={r} | {line}")
```

### 前処理の使い分け

| ファイル | 用途 |
|---------|------|
| `/tmp/condensed.txt` | **通読用。** まずこれを頭から最後まで読んで配信全体の流れを掴む。60分の配信でおよそ400行に収まる |
| `/tmp/timeline.txt` | **時刻確定用。** シーンを決めた後、`grep` で該当発言を引いて秒単位の正確な時刻を確定する |

**OCRモードでは集約窓とチャット照合窓が自動的に広がる**（集約20秒→30秒、照合 -15/+30秒→ -20/+60秒、スパイク集計30秒→60秒）。チャット時刻が丸められている以上、狭い窓で照合すると取りこぼすためである。その分 condensed.txt の行数は少なくなるが、通読すべき範囲は変わらない。

出力に含まれるユーザー名は運営アカウントの特定など**内部判断にのみ**使い、最終出力には決して載せない。

## タイムスタンプ選別基準

| カテゴリ | 具体的なシグナル | 優先度 |
|---------|----------------|--------|
| **ハプニング・事件** | エラー・バグ・予期しない展開（運営 `#` の訂正・謝罪も含む） | 高 |
| **感動シーン** | チャットに「泣いた」「エモ」「いい話」が集中 | 高 |
| **笑いどころ・ネタ** | チャットに「草」「ｗ」「マジか」が集中 | 中 |
| **正解・不正解の盛り上がり** | クイズ・ゲーム系での正解発表、チャットが沸く瞬間 | 中 |
| **話題の転換点** | コーナーの開始、運営 `#` による「次の問題」などの節目 | 低 |
| **視聴者参加の見せ場** | 順番待ち `@` コメントへの返答、視聴者との特定のやりとり | 低 |

## 配信時間別タイムスタンプ数の目安

| 配信時間 | 個数 |
|---------|------|
| 30分以下 | 10〜15 |
| 30〜60分 | 20〜30 |
| 60分以上 | 30〜50 |

**この数値はあくまで目安であり、ノルマではない。** 数を埋めるために中身の薄いタイムスタンプを量産してはならないし、逆に見どころが密集している区間を上限に縛られて切り捨ててもならない。

- 淡々と進む配信なら目安を下回ってよい
- 面白い展開が連続する区間は、2〜3分に複数個並んでも構わない
- 判断基準は常に「そのタイムスタンプを見て、視聴者がクリックしたくなるか」の一点
- 数合わせで入れた説明が 1 つでもあると目次全体の信頼度が落ちる。**削る方を優先する**

## シーン説明の作成ルール

### ルール1: 「要約」ではなく「予告（チラ見せ）」にする【最重要】

オチ、発言の答え、ハプニングの結末など、**それを読んで満足してしまう内容は絶対に書かない。** 「好奇心の空白（Curiosity Gap）」を刺激し、クリックしたくなる寸止め表現にする。

- 良い例: `[28:30] まさかの爆弾発言でチャット凍りつく`
- 悪い例: `[28:30] 〇〇は嫌いだと発言し爆笑`（オチを書き切っているためNG）

### ルール1補足: 「謎かけ→即答え」の連続ネタバレを防ぐ【最重要】

**「謎かけ」タイムスタンプの直後に「答え」タイムスタンプを置かない。**

- NG: `[5:50] チャットを惑わす第1問` → `[6:37] 「牛乳を注ぐ女」スタート`
- OK: `[5:50] チャットを惑わす第1問` → `[6:37] ようやく合点がいったチャット欄`

連想ゲーム・クイズの答え・ハプニングの顛末を列挙する説明はNG。

### ルール2: 自動文字起こしの誤変換を出力に持ち込まない【最重要】

sbv ファイルは自動文字起こしであり、**固有名詞・専門用語・早口部分は高確率で誤変換されている。** 実例:

- 「しずく」→ しず子 / 雫し / 静 / しく / しずの / 水
- 「あき先生」→ 秋先生 / 秋先線 / 全キさん
- 「SpaceX」→ スパセックス、「機種変」→ 機種編、「有言実行」→ 有限実行

守るべき規則:

1. **人物名・固有名詞は必ず正規表記に直して出力する。** 誤変換をそのまま見出しに使わない
2. **意味を確定できない崩れた行を起点にタイムスタンプを作らない。** 前後の文脈と繋がらない、明らかに文が壊れている、といった行は「配信者がおかしなことを言った」のではなく**単なる文字起こしの失敗**である可能性が高い
3. 特に「配信者が矛盾したことを言った」「言い間違えた」「自爆した」という趣旨の説明を書きそうになったら、**それは誤変換を実在の発言と誤認している疑いを最優先で検討する。** 前後 30 秒を読み直し、確証が持てなければそのシーンごと落とす
4. チャットの反応が裏取りに使える。本当に配信者が言い間違えたなら、チャットが必ず反応している。チャットが無反応なら誤変換と判断してよい
5. 同じ語句・固有名詞が sbv 内に複数回、同じ形で繰り返し出現している場合は書き起こし精度が高いと判断してよい（ランダムな誤変換は毎回異なる崩れ方をする傾向がある）。1回しか出現しない崩れた固有名詞は特に慎重に扱う
6. **通常版の live_chat** は視聴者の手入力であり文字起こし誤りが起こり得ない。sbv 上の固有名詞に確信が持てない場合、同じ語句を複数の視聴者が独立して live_chat 内で言及していないか確認する。複数人が同じ語句を使っていれば、実際に話題になった証拠として扱ってよい
7. **ただし OCR復元版（live_chat_ocr）はこの裏取りに使えない。** 画面から読み取った文字であり、視覚的に似た文字に化けうる。しかも全員が同じフォント・同じ描画で表示されているため、**複数人が同じ語を書いていても全員が同じ形に誤読される。**「複数人が同じ表記で書いている＝正しい」という推論は OCR では成立しない。逆に、音声認識（sbv）と OCR は誤りの発生源が独立しているので、**両者が同じ表記で一致していれば**信頼度は上がると考えてよい

**迷ったら書かない。** 誤変換由来の説明は事実無根の記述であり、ハルシネーションと同じ扱いになる。

### ルール3: 熱心なリスナー目線のトーン

事務的な議事録ではなく、配信を楽しんでいるファンの目線で書く。「草」「エモい」「限界化」「沼る」など配信カルチャーの語彙を自然に使う。

### ルール4: 適切なトピックの粒度を保つ

「雑談」「ゲーム開始」など中身が想像できない大雑把な見出しは避ける。些細な出来事を2〜3分ごとに並べる細かすぎる見出しも避ける。

### ルール5: 簡潔さを優先

1つのシーン説明は **1〜2行（最大30文字程度）** に収める。

### ルール6: チャット反応を活用

その時刻前後のチャットから意味を読み取り、説明に反映させる。

- 例: sbv が「叩いてアピールします」のみでも、チャットが「痛くないですｗ」で沸いていれば → `謎のアピール方法にチャット突っ込みどころ満載`
- **OCRモードでは照合窓が広い（-20〜+60秒）ぶん、無関係なコメントが混ざりやすい。** そのチャットが本当にその発言への反応かを sbv の前後で確かめてから説明に反映する（ルール11）

### ルール7: 重要な人物名は記載

複数人が登場する配信では、誰のアクション・発言か明記する。

### ルール8: センシティブな話題の扱い

下ネタ・際どい話題は、**面白い盛り上がり方をしていない限り、そもそも取り上げない。** 配信中に一定時間その話題が続いていたとしても、タイムスタンプにする義務はない。無視してよい。

そのうえで、**面白く盛り上がっていた場合でも次は絶対に出力しない**:

- 配信者が無理をして捌いているであろう、閉鎖的で無自覚なセンシティブないじり
- 視聴者による無自覚ないじめの構造になっているやりとり
- 配信者が困っている・受け流している状態を「盛り上がり」と誤認したもの

チャットが沸いているかどうかだけで判断してはならない。**いじる側が盛り上がっているだけの場面は、盛り上がりではない。** 配信者側が明確にノって展開を広げている場合のみ、取り上げてよい。

取り上げる場合も、直接的な語を見出しに使わず「持論が展開される」程度の匂わせに留め、切り抜き的に強調しない。

### ルール9: タイムスタンプは必ず sbv の発言か運営 `#` コメントを起点にする【ハルシネーション防止】

- 各タイムスタンプは、対応する sbv の発言エントリ、または運営者の `#` コメント（節目・補足・進行情報）を必ず起点にする
- live_chat の視聴者コメントは「チャット反応の補足情報」として参照してよいが、**それだけを根拠にタイムスタンプを作ってはならない**
  - NG: 視聴者の `#感想` や通常コメントが面白くても、しずくの対応発言が sbv に無い場合
  - NG: `@質問コメント` が投稿されたが、しずくが応答しないまま流れた場合
- 「チャットが面白い」だけでは不十分。**しずくが実際に発言した証拠**（対応時刻の sbv エントリ）を確認してから説明文を書く
- sbv の内容が読み取れない時間帯は、その区間のタイムスタンプ数を絞り、確認できた範囲のみ記載する

### ルール10: 効果的な見出しテクニック

- **配信者本人の一言を「」で直接引用する**と、地の文の要約より雰囲気が伝わりクリックを誘発しやすい（例: `「AIは絶対に間違えません」しずくの強気な発言にチャット総ツッコミ`）。ただし引用する一言そのものが「オチ・正解・核心」である場合、引用すること自体がルール1違反になる。「〇〇と発言→実は△△だった」のように発言と答え合わせを同じタイムスタンプに並べないこと
- **「行動→反応」を矢印でつなぐ**と、結果の中身を明かさず「何かが起きた」ことだけを圧縮して伝えられる（例: `査定を実施→チャット崩壊`）。多用すると単調になるため他の文体と混ぜる
- **配信・コーナー名物の決め台詞やコール**（例: 発表前の煽り文句、オープニングの掛け声）が sbv に繰り返し出現する場合、見出しに取り入れると常連視聴者に伝わりやすい

### ルール11: OCRモードでは「チャットが根拠」の比重をさらに下げる

`live_chat_ocr` しか無い回では、チャットは**取りこぼしと誤読を含む断片**である。次を守る。

1. **出力の時刻は必ず sbv 側で確定する。** チャットの `[0:02:15]` をそのまま見出しの時刻に使わない。OCRの時刻は丸め済みの上限値であり、実際の出来事はそれより前にある
2. **チャットの件数を「盛り上がりの証拠」として断定しない。** 画面に写った分しか無いため、件数は実数より少なく、大盛り上がりの区間ほど頭打ちになる。「チャット欄が一瞬で流れた」「コメントが止まらない」といった**流速を根拠にした表現は書かない**
3. **チャットのコメント文面をそのまま引用しない。** 誤読されている可能性がある。反応の"傾向"（笑っている／驚いている／心配している）を読み取る用途に留める
4. **同一タイムスタンプ内のコメントの前後関係から因果を読まない。** 15秒バケット内の並びは投稿順を保証しない。「Aの発言→即座にBの反応」といった構成は、sbv 側で確認できる場合のみ書く
5. **チャットが薄い区間を「盛り上がらなかった」と解釈しない。** 単に拾えなかっただけの可能性が高い。その区間は sbv の内容だけで淡々と判断する
6. `#` コマンドが0件でも、info の概要欄にコマンド説明があるなら**OCRで記号が脱落した可能性**を先に疑う。`references/command-driven-chat.md` の0件時の手順に従う

**OCRモードでもタイムスタンプの個数目安・品質基準は変えない。** チャットが薄いことを理由に説明を薄くするのではなく、sbv の通読精度で補う。

## 出力形式

YouTube コメント欄は文字数が多いと「続きを読む」で折りたたまれる（目安は約4000文字）。**折りたたまれない冒頭部分に最も魅力的なハイライトと注意書きを配置する。**

コピペしやすいよう、**全体を1つのコードブロックにまとめて**チャットに出力する。ただしタイムスタンプをただ並べるとリズムが単調になるため、「オープニング～〇問目」のような見出しで、配信の構成（コーナー単位・問題単位）に沿ってセクション分けする。

```
【タイムスタンプ集】① オープニング～〇問目
🌟ハイライト：[MM:SS] （このパートで最も気になるシーンの寸止め説明）
※これは自動文字起こしからAIによって生成したタイムスタンプのため、ネタバレや誤り、時間のズレを含む可能性があります。

[MM:SS] シーン説明
[MM:SS] シーン説明
…

【タイムスタンプ集】② 〇問目 ～ 〇問目
🌟ハイライト：[MM:SS] （このパートの目玉シーン）

[MM:SS] シーン説明
…
```

- 注意書きは**コードブロック全体の冒頭にのみ**記載する
- **🌟ハイライトに挙げたシーンは、本文のリストにも同じ時刻・同じ説明で再掲する。** 各セクションにリズムを持たせるため、セクションごとに1つ設定する
- **🌟ハイライトは、単なる進行の節目（新コーナー開始・企画告知など）ではなく「結果や顛末が気になる」フック性のあるシーンを優先する。** 節目自体をハイライトにする場合は、意外な展開・対立・驚きなど気になる要素を言い回しに含める
- タイムスタンプ形式は 60 分未満なら `[MM:SS]`、超える場合は `[H:MM:SS]` を使用する
- セクション分けは配信の構成（コーナー単位・問題単位）に沿わせる。構成が単純な配信ならセクション分け不要
- 1 セクションあたり 10〜15 個が読みやすいが、これも目安。コーナーの区切りを優先する。**ただし20個を超えそうな場合は、名前付きコーナーの区切りがなくても「オープニング雑談」と「本編開始」のような自然な流れの切れ目でさらにセクションを分ける。コーナー優先を理由に1セクションを肥大化させない**
- **配信終盤の定型的な挨拶やコール練習など、内容が繰り返しになるだけの区間は、特筆すべき要素がない限りタイムスタンプ化を省略してよい**

## 禁止事項

- [ ] オチ・結末・発言の核心など「ネタバレ・完全な要約」を記載しない（チラ見せに徹する）
- [ ] 「謎かけ」直後のタイムスタンプで答えを書く「連続ネタバレ」をしない
- [ ] ログに存在しない事象や発言を推測・捏造（ハルシネーション）しない
- [ ] **自動文字起こしの誤変換をそのまま見出しに使わない**（人物名・固有名詞は正規表記に直す）
- [ ] **意味を確定できない崩れた行を根拠にタイムスタンプを作らない**（誤変換を実在の発言と誤認しない）
- [ ] **配信者が無理をして捌いている、無自覚ないじり／いじめ構造のやりとりを取り上げない**
- [ ] sbv の発言テキストをそのまま丸写しにしない
- [ ] 「雑談」「ゲーム開始」など中身が想像できない大雑把な見出しを作らない
- [ ] 個数の目安を埋めるためだけの、中身の薄いタイムスタンプを作らない
- [ ] 個人特定につながる内容を記載しない
- [ ] チャットのユーザー名（運営アカウント含む）を出力に含めない
- [ ] 説明を3行以上にしない
- [ ] YouTube のリンクやスパムコンテンツを紛れ込ませない
- [ ] sbv で対応する発言を確認せず、live_chat の視聴者コメント単独を根拠に説明文を作らない
- [ ] `.srt` ファイルを参照しない
- [ ] **OCRチャットの粗いタイムスタンプを、そのまま出力の時刻に使わない**（時刻は必ず sbv 側で確定する）
- [ ] **OCRチャットの件数・流速を根拠に「チャットが爆速で流れた」等と書かない**（画面に写った分しか無い）
- [ ] **OCRチャットの文字列を固有名詞の裏取りに使わない**（全員が同じ形に誤読されうる）
- [ ] 通常版とOCR版の live_chat を同時に読み込んで二重計上しない

## 出力品質チェックリスト

出力前に必ず全項目を確認する。

- [ ] 既存目次・公式チャプターの充実度を読んで判断したか。不足時はコメントを再取得し、追加が必要な範囲と理由を示したか
- [ ] 投稿待ち・投稿済み公開未確認の案を重ねて作っていないか。投稿はユーザーの手動操作として引き渡したか
- [ ] 投稿後の再取得は最低限2〜3分（運用上3分）空けたか。確認日時を残し、後日の非表示も確定原因なしに扱ったか
- [ ] YouTubeとFandomの照合やWiki更新を、このスキルの必須手順に混ぜていないか

- [ ] 前処理スクリプトが sbv を正常に読めていたか（0件でないことを確認したか）
- [ ] OCRモードだった場合、時刻をすべて sbv 側で確定したか。チャットの丸め時刻を流用していないか
- [ ] OCRモードだった場合、チャットの件数や流速を盛り上がりの根拠にした表現が混ざっていないか
- [ ] condensed.txt を最初から最後まで通読し、配信で扱われた話題をすべて把握できているか（雑談パートも含め、読み飛ばした区間がないか）
- [ ] シーン説明が動画のオチを明かしておらず、「好奇心の空白」を刺激する予告になっているか
- [ ] 「謎かけ」直後に答えになるタイムスタンプを置いていないか（隣接タイムスタンプを前後で読み直して確認）
- [ ] 人物名・固有名詞が誤変換のまま残っていないか
- [ ] 「配信者が言い間違えた／矛盾した」系の説明を書いていないか。書いたなら誤変換でないと確証があるか
- [ ] センシティブな話題を、配信者がノっていない状態で取り上げていないか
- [ ] 冒頭ハイライト配置など、YouTube の「続きを読む」UI を考慮した構成になっているか
- [ ] 注意書きが「※これは自動文字起こしからAIによって生成した〜時間のズレを含む可能性があります。」になっているか
- [ ] 配信カルチャーに沿ったリスナー目線のトーン（Vibe）が反映されているか
- [ ] タイムスタンプが大雑把すぎず、細かすぎない粒度か
- [ ] ハプニング・感動・笑いどころなど重要ハイライトが含まれているか
- [ ] すべてのタイムスタンプが `[MM:SS]` または `[H:MM:SS]` 形式か
- [ ] sbv と live_chat の時刻をきちんと突き合わせているか
- [ ] 運営 `#` コメントを節目・補足として正しく活用し、ユーザー名は出力に含めていないか（コマンド未使用の配信では定型句からコーナーを検出したか）
- [ ] 各タイムスタンプの説明が sbv の対応発言または運営 `#` コメントを起点にしているか
- [ ] 数合わせで入れた中身の薄いタイムスタンプが混ざっていないか
