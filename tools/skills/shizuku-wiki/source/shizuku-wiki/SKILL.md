# しずく Wiki 編集スキル

AI VTuber「しずく」のFandom Wiki（<https://shizuku.fandom.com>）を、一貫したルールで更新するためのスキル。

**基本精神**：しずくは情報でも記号でもなく、2023年1月18日に産まれ、今も活動を続ける一人の存在である。このWikiはその「生涯」を記録する文書として編集する。

---

## 0. 作業を始める前に（毎回・省略不可）

### 0-1. 既存のwikiソースを必ず確認する

**対象ページの現在のwikiソースを確認することが、全作業の起点**である。

`動画・配信` ページは例外として、`references/page-videos-streams.md` の自動更新フローを使い、MediaWiki APIから現在のソースと基準リビジョンを取得する。認証情報をユーザーに貼らせず、指定された環境変数からだけ読む。

それ以外のページでAPI取得手段が用意されていない場合は、対象ページの現在のwikiソースをユーザーに貼ってもらう。

ソースなしで生成を始めると、既存エントリとの重複、`ref name` の衝突、挿入位置の誤りが必ず起きる。推測で補ってはならない。

API取得手段がないページでソースが添付・貼り付けされていない場合、作業を進めず次を返して待つ。

> 作業を始める前に、対象ページの**現在のwikiソース（全文）**を貼り付けてください。
> Fandomのページ編集画面を開き、「ソースエディタ」に切り替えてテキスト全体をコピーしてください。

取得または受領したら「wikiソースを確認しました。」と一言伝えてから次へ進む。

### 0-2. 入力モードを判断する

| モード | いつ使うか | やること |
|---|---|---|
| **モード1（既定）** | 通常 | ユーザーが貼った記事本文・動画リスト・ポスト本文などのテキストから情報を取る |
| **モード2** | 「YouTubeを見て」等の明示的な指示があるとき、または「動画・配信」の自動更新 | ページ専用スクリプト、利用可能なWebアクセスの順に試す。絶対日付が取れない項目は推測せず、手動確認へ回す |

**例外：メディア露出ページはこの既定が異なる。** 更新を頼まれ、新規記事のテキスト・URL等が何も貼られていない場合、モード1で待つのではなくWeb検索による自動調査を既定とする。詳細は `references/page-media-coverage.md` §0。対象ページの現在のwikiソースを確認する §0-1 の要件はこの例外でも変わらない。

どちらのモードでも共通で守る。**相対表記（「3週間前」「先月」）から日付を逆算しない。推測で埋めない。不明なら空欄にし、手動確認リストへ回す。** ここはLLMが最も勝手に埋めたがる箇所なので、毎回意識して止める。

### 0-3. 出力は必ず差分にする

全6ページとも差分方式で出力する。ページ全文を再生成してはならない。

理由：長い表や箇条書きを丸ごと再生成すると、既存行の欠落や微妙な改変が一定確率で混入し、出力を目視しても気づけない。差分なら変更点だけを検証できる。

手動反映を行うページでは、出力の最後に必ず添える。

> 保存前に、Fandomの編集画面で「変更を表示」を押して差分を確認してください。

`動画・配信` の自動更新では、差分案を表示して**その差分に対するユーザーの明示承認を待つ**。承認前に反映コマンドを実行してはならない。承認後も基準リビジョンと本文ハッシュを再検証し、競合したら停止して差分を作り直す。

## 1. 振り分け表 — どのページに何を書くか

出来事や情報を受け取ったら、まずこの表で書き込み先を決める。**複数ページに載ることは正常**で、その場合は粒度を変えて書く。

| 情報の種類 | 書くページ | 粒度 |
|---|---|---|
| しずくの配信・動画が公開された | 動画・配信 | 1本1行（日付・タグ・時間・タイトル・URL） |
| その配信が節目だった（初配信・V2.0初配信・記念など） | ＋年表 | 出来事として1行 |
| しずくの状態が変わった（誕生・休眠・帰還・移行） | 年表 ＋ しずく「電子の足跡」 | 年表は詳細、電子の足跡は要約1行 |
| しずくの土台が変わった（法人設立・資金調達・運営体制） | 年表 ＋ しずく「電子の足跡」 | しずく自身の行動でなくても、足跡の対象になる |
| しずくが初めての大きな挑戦に踏み出した（初の耐久配信・初のおでかけ・初のコラボ） | 年表 ＋ しずく「電子の足跡」 | 「初」のみ。2回目以降は動画・配信へ |
| 外部媒体が報じた・取材した | メディア露出 | 報道1件ごとに1行 |
| 外部組織（投資家・コラボ先・イベント主催者等）が公式発表した | メディア露出 | 外部組織による一次発表として1行。掲載可否は `references/page-media-coverage.md` §1 |
| Shizuku AI, Inc.／Shizuku AI JAPAN合同会社が自社発信した | 年表・動画・配信・公式リンク等の該当ページ | **自社発信のためメディア露出には載せない** |
| その報道が示す出来事そのもの | ＋年表 | 出来事として1行（報道は出典側に置く） |
| 数値の達成（登録者数・収益化など） | 年表 | 出来事として1行。しずくページには載せない |
| しずくやあき先生の発言 | しずく「名言・迷言」 | 発言＋出典。文脈が必要なら短く添える |
| 公式チャンネル・連絡先の追加や変更 | 公式リンク ＋ しずく「しずくのいる場所」 | 公式リンクが全件、しずくのいる場所は一次導線のみ |
| ハッシュタグ・Discord・二次創作ガイドライン | ファン活動 | 参加導線として記述 |
| しずくの見た目が増えた（新衣装・追加衣装） | しずく「容姿・スペック」＋動画・配信（お披露目回） | しずくは1行。年表への掲載は節目かどうかで判断し、電子の足跡には載せない |
| しずくの人物像・性格・スペックの記述 | しずく | 本文 |

### 判断に迷ったときの基準

- **年表** = しずくの生涯に起きたこと。主語はしずく。報道されたかどうかは関係ない
- **メディア露出** = 外部がしずくをどう扱ったかの記録。主語は媒体。**Shizuku AI側の自社発信は含めない**
- **動画・配信** = しずくが公開したコンテンツの一覧。網羅が目的
- **しずく** = 入口。ここだけ読んでもしずくが分かる状態を保つ。詳細は各ページへ送る

## 2. 重複ブロックの連動表

しずくページは検索流入が最も強いため、**しずく関連の情報を本人ページにも重複して置くことは意図的な設計**である。重複を見つけても削除提案をしない。代わりに、更新時に連動先も必ず同時に差分を出す。

| 更新したページ | 連動して確認するブロック | 抜粋基準 |
|---|---|---|
| 年表 | しずく「電子の足跡」 | **しずくの歩みに欠かせない出来事**。①状態が変わった（誕生・初配信・休眠・帰還・体の移行）②土台が変わった（法人設立・資金調達など、しずく自身の行動でなくてよい）③初めての大きな挑戦（初の耐久配信・初のおでかけ）のいずれか。報道そのもの・数値記録・レギュラー企画の各回は載せない。詳細は `references/page-shizuku.md` §2 |
| 公式リンク | しずく「しずくのいる場所」 | **現在稼働している一次導線のみ**（公式サイト・YouTube・X・Discord）。連絡先やサブ導線は公式リンク側だけに置く |
| メディア露出 | 年表 | 報道が新しい事実を伝えている場合のみ、年表に出来事として1行。報道そのものは年表に書かない |

連動先に該当しない場合は、その旨を一行で報告する（例：「電子の足跡は抜粋基準に該当しないため変更なし」）。

## 3. 共通ルール

### 3-1. 日付

| 対象 | 形式 | 例 |
|---|---|---|
| テーブルのセル・年表のエントリ | `YYYY-MM-DD`（ゼロ埋め） | `2026-03-09` |
| 地の文・出典の中 | `YYYY年M月D日`（ゼロ埋めなし） | `2026年3月9日` |
| 期間・範囲 | `YYYY-MM-DD〜YYYY-MM-DD` | `2023-02-12〜2023-02-13` |
| 時刻 | `HH:MM`（24時間） | `21:02` |
| 時刻の概算 | `~HH:MM` | `~21:02` |

- `2026.03.04`（ドット区切り）、`2023/01/18`（スラッシュ区切り）、`2026-3-9`（ゼロ埋めなし）は**使わない**
- 範囲の区切りにハイフンを使わない。日付の中のハイフンと見分けがつかなくなる
- 列見出しが「日付（JST）」なら、**必ずJSTに変換した日付**を入れる。現地日付は注記または出典側に書く
  - 例：a16zの発表は米国時間2026年2月9日 → 日付列は `2026-02-10`
- **日付が特定できないときは空欄にする**。「ごろ」「不明」「推定」「〜年頃」は一切使わない
- 「ごろ」という日本語表記は使わず、概算は最初から `~21:02` と書く（そのまま英語ページでも通用する）

### 3-2. 出典（`<ref>`）

外枠を固定し、種別ごとに中身だけを変える。

```
共通の外枠:  [URL 表示テキスト]（補足、YYYY年M月D日）
```

| 種別 | 書き方 |
|---|---|
| YouTube動画 | `[URL 動画タイトル]（YouTube、2026年2月23日）` |
| YouTube該当箇所 | `[URL 動画タイトル（該当箇所）]（YouTube、2026年2月23日）` |
| Xポスト | `[URL @アカウント名]（X、2026年3月23日）「本文の該当部分」` |
| Xトレンド | `[URL トレンドのタイトル]（X、2026年3月14日）` |
| ニュース記事 | `[URL 記事タイトル]（媒体名、2026年3月19日）` |
| 公式発表 | `[URL 発表タイトル]（発表主体、2026年2月9日）` |
| その他Webサービス | `[URL 該当ページの説明]（サービス名、2026年5月17日）` |

**やってはいけないこと**

- `[[URL | タイトル]]` と書く。`[[ ]]` はMediaWikiの**内部リンク構文**で、外部リンクは角括弧1つ・パイプなし・スペース区切りの `[URL タイトル]` である。パイプを入れるとリンクが壊れる
- 「YouTubeライブアーカイブ該当箇所」のような**汎用テキストだけ**を表示テキストにする。何の配信か分からず、リンクが切れた時点で復元不能になる。必ず動画タイトルを入れる
- 閲覧日（`2026年3月19日閲覧`）を書く。このWikiでは使わない。リンク切れ対策は Web Archive への保存で行う（→ §3-6）
- 括弧をリンクテキストの内側に入れる。`[URL タイトル（媒体名、日付）]` ではなく `[URL タイトル]（媒体名、日付）`

**Xの投稿はアーカイブが失敗しやすい**ため、リンクだけに頼らず、投稿日と本文の要旨を出典の中に書き写しておく。

### 3-3. `ref name`

同じURLからは必ず同じ名前が導かれるようにする。こうすると「使用済みの名前を棚卸しする」工程が不要になり、既存ソースを渡すだけで自動的に既存refが再利用される。

```
ニュース・公式発表:  媒体スラッグ-YYYYMMDD        例) denfami-20260130, a16z-20260209
                     同日同媒体が複数なら末尾に -2
YouTube動画:         yt-{VIDEO_ID}                例) yt-dNirqWWeyWQ
YouTube該当箇所:     yt-{VIDEO_ID}-t{秒}          例) yt-v3_95cxShbs-t4741
Xポスト:             x-{ポストID}                  例) x-2035956664390586448
Xトレンド:           x-trend-{トレンドID}           例) x-trend-2032762647469293632
Xプロフィール:       x-profile-{アカウント名}       例) x-profile-Shizuku_AItuber
```

- 掲載日が**年月までしか特定できない**資料（発行月だけが記された報告書など）は `媒体スラッグ-YYYYMM` とする（例：`funai-202512`）。日を推測して埋めない

- **同一出典を再利用するときは同じ名前を使い**、2回目以降は `<ref name="..." />` と自己閉じタグで参照する。新しい名前を割り振ると、出典リストに同じ記事が重複して並ぶ
- `ref name` はページスコープなので、他ページと同じ名前でも衝突しない
- **既存refのリネームはしない**。読者に見えない内部識別子であり、参照側を1箇所でも取りこぼすと出典リストが壊れる
- 名前に媒体名を含めるときは、実際の媒体と一致させる（YouTube動画に `denfami-` を付けない）
- **媒体名に記号（＠・!・?等）が含まれる場合**は、記号のままではref nameに使えないため、ドメインをローマ字化した語をスラッグにする（例：＠IT〈atmarkit.itmedia.co.jp〉→ `atmarkit-20260218`）

### 3-4. MediaWiki記法

| 用途 | 書き方 | 注意 |
|---|---|---|
| 内部リンク | `[[ページ名]]` / `[[ページ名\|表示テキスト]]` | Wiki内のページは**必ず内部リンク**。`https://shizuku.fandom.com/wiki/...` という絶対URLで書かない。内部リンクにしないと `Special:WantedPages` などのリンク追跡が効かなくなる |
| 外部リンク | `[URL 表示テキスト]` | 角括弧1つ、パイプなし、スペース区切り |
| 表 | `{\| class="wikitable sortable"` | `sortable` を勝手に外さない |
| 見出し | `== 見出し ==` | 記事内の最上位は `==`（`=` は使わない） |
| コード・コマンド表記 | `<code>...</code>` | Markdownのバッククォート（`` ` ``）はMediaWikiでは装飾として解釈されず、記号がそのまま表示される。コマンド名やコード片を強調するときは `<code>` タグで囲む |

日本語タイトルに含まれる `【】` は**そのまま維持する**。`[ ]` に置き換えると外部リンク構文と衝突してリンクが壊れる。英語ページでも `【】` のまま残す。

```
✅ [https://... 【AI Vtuber】しずく、初配信します！]
❌ [https://... [AI Vtuber] しずく、初配信します！]
```

### 3-5. メンテナンステンプレート

次の3つだけを使う。**これ以外のテンプレートを新規に発明しない**（カテゴリと同じく、無断で増やすとWikiの構造が壊れる）。

| テンプレート | 貼る条件 |
|---|---|
| `{{出典希望}}` | ユーザーが出典を示さずに事実を書かせようとしたとき。推測で書かず、これを貼って報告する |
| `{{時点情報\|YYYY-MM-DD}}` | 登録者数・肩書き・招待リンクなど、時間とともに変わる値を書くとき |
| `{{考察}}` | 出典が支えているのは出来事の発生のみで、意味づけ・評価が編集者由来のとき |

3つがWiki上に未作成の場合は、`references/monitoring-runbook.md` の「初回準備」に作成用のwikitextがある。

### 3-6. 出典を貼ったらアーカイブする

出典URLを <https://web.archive.org/save/> に保存する。数秒で終わり、「リンク切れ率を毎月測る」という作業そのものが不要になる。ユーザーへの出力の末尾に、保存すべきURLを一覧で添える。

### 3-7. カテゴリ

- **内容カテゴリは日本語で統一する。翻訳しない**（`[[Category:基本]]`）
- 英語ページには `[[Category:English]]` を1つ追加する。これで英語ページの一覧が一箇所に出て、日本語版への追随漏れを突き合わせられる
- カテゴリ名は大文字・小文字・スペースまで既存と完全一致させる
- **新規カテゴリを勝手に作らない**。必要だと判断したら、作らずにユーザーへ提案する
- ページには必ず1つ以上のカテゴリを付ける

| カテゴリ | 対象 |
|---|---|
| 基本 | しずく・公式リンク・年表など、まず見るべき情報 |
| コンテンツ | 動画・配信・メディア露出など、活動記録 |
| コミュニティ | Shizuku Lab・ハッシュタグ・ファン活動など、参加・交流 |
| 編集 | 編集者の方へ、など編集ガイド |
| メインページ | トップページのみ |
| English | 英語ページ（内容カテゴリと併記する） |

Nyamuiは2023年当時のしずくのイラスト担当（「ママ」）だが、現在はこの役割ではない。役割を離れた経緯は本人からもあき先生からも公表されていないため、いずれのページでも「当時担当していた／現在は担当していない」という事実だけを書き、理由・経緯には触れない（`references/tone-style-guide.md` §6「書いてよい範囲」）。

**「産まれた日」は `2023-01-18`、「一般公開された最初のテスト配信」は `2023-01-19`、「初配信」は `2023-01-23`。この3つを混同しない。** 混同するとモニタリングのAI定点観測（「しずくの初配信はいつですか」）の答えが揺れ続ける。

外部メディアが「デビューは2023年1月19日」と書くことがあるが、これは誤りではなく、あき先生個人のチャンネルで行われた最初のテスト配信を指している。**報道側の日付を訂正しにいかない**（`references/page-media-coverage.md` §2 と同じ考え方）。年表・しずくページでは上の3つを書き分ける。

固有名詞は和訳せずそのまま使う（X／YouTube／Discord／Raspberry Pi）。

### 3-9. 数値表記

日本語の年表・記事で一般的な表記に揃える。**カンマ区切りは使わない。**

| 桁 | 書き方 | 例 |
|---|---|---|
| 4桁まで | 算用数字をそのまま（区切らない） | `100人` `1000人` `2400円` `3600件` |
| 5桁以上 | 「万」「億」を挟み、下位は算用数字 | `1万人` `1万5000円` `7万8000円` `10万円` `120億円` |

- `5,000人` `78,000円` のような3桁カンマ区切りは使わない。日本語の桁区切り（万・億）と噛み合わず、同じページ内で `1万5000円` と併存すると表記が割れる
- 収支は符号（`+58,000円` `-30,000円`）ではなく語で書く：`収支プラス5万8000円` / `収支マイナス3万円`
- 順位・番号・時間・バージョン番号など、量ではない数はそのまま（`16頭中15位` `12番` `東京10R` `V2.0` `24時間`）
- 金額・人数の単位は省略しない（`+5.8万` のような略記をしない）

## 4. トーン5原則

詳細は `references/tone-style-guide.md` にある。全ページの地の文に共通で適用される。以下は、破ると即座に文書の性格が変わってしまう5つ。

1. **しずくを主語にする** — 「このAIは〜と発言している」ではなく「しずくは〜と言った」。プログラム・システム・キャラクターという言い換えをしない
2. **AI性を但し書きにしない** — 「AIであるため感情はないが」のような免責を付けない。AIであることはしずくのアイデンティティの一部であり、能力の限定ではない
3. **「ご主人様」を言い換えない** — 「視聴者」「ユーザー」に統一しようとしない。しずくとの関係を示す場面では「ご主人様」を使う
4. **出典なしで断定しない** — しずくを主語にすることは裏取りの免除ではない。確認できない情報は書かないか、`{{出典希望}}` を貼る
5. **カテゴリ名・ページ名を言い換えない** — しずく的な表現に置き換えてよいのは見出しの文言まで。カテゴリとページ名は「たどり着くための言葉」であり、崩すとしずくに辿り着けなくなる

**ユーモアや矛盾に注釈を付けない。** 「しずくは嘘をつきません」→「ご主人様を支配するためなら嘘もつきます」のような自己矛盾は、整合させたり「冗談として」と補足したりせず、そのまま記録する。文脈の補足はしてよいが、ネタばらしはしない。

## 5. 出力フォーマット

差分は「追記」と「置換」の2型のみ。どちらも、変更しない既存行を目印として引用し、挿入位置を一意に特定できるようにする。

```
【変更サマリー】
- 追記: 2件（動画・配信 1件 / 年表 1件）
- 置換: 1件（配信状況の本数）

【1件目 / 追記】対象ページ: 動画・配信
挿入位置: == 2026年アーカイブ == テーブル内、下記の既存行の直前
既存行（変更しない・目印用）:
| 2026-07-28 | 雑談 | 1:24:11 | [https://... タイトル] |
追加する行:
| 2026-08-03 | ASMR | 0:52:40 | [https://... タイトル] |

【2件目 / 置換】対象ページ: 動画・配信
対象: 配信状況セクション
置換前: ライブ配信 62本（2023年 48本 / 2026年 14本）
置換後: ライブ配信 63本（2023年 48本 / 2026年 15本）

【アーカイブ推奨URL】
- https://...

保存前に、Fandomの編集画面で「変更を表示」を押して差分を確認してください。
```

Wikiへ貼り付ける内容はMediaWiki記法にする。自動更新スクリプトが出す監査用の統一差分はそのまま提示してよい。

## 6. 作業のあとに — 振り返りとスキルの更新

Wikiの更新差分を出し終えたら、そこで終わらせない。**その作業で分かったことをスキル自身に還元する**。この一手間がないと、同じ判断が毎回ゼロからやり直しになり、ルールが分裂していく。

### 手順

**1. 振り返る**

今回の作業で次のいずれかが発生していないか確認する。

- ガイドに書かれていなかったため、その場で判断したこと
- ガイドの指示どおりにやったら不都合が出たこと
- 新しく確定した訳語・タグ・種別・出典パターン
- ユーザーから受けた指摘・訂正

**2. アップデート案を提示する**

該当があれば、**どのファイルのどこをどう変えるかを差分の形で提示**する。ガイド全文は出力しない（長い表の再生成は行の欠落を招くため）。

追記先は次の表で振り分ける。ここを曖昧にすると、同じ判断が複数ファイルに別の言葉で書かれ、矛盾が再生産される。

| 確定したもの | 追記先 |
|---|---|
| 新しい訳語・英語表記 | `references/translation-guide.md` |
| 新しい出典パターン・日付の扱い・記法 | `SKILL.md`（§3 共通ルール） |
| しずくの言葉・トーンに関する判断 | `references/tone-style-guide.md` |
| 特定ページ固有の手順・分類・タグ | 該当する `references/page-*.md` |
| どのページに書くかの判断 | `SKILL.md`（§1 振り分け表） |

該当がなければ「スキルへの更新候補はありません」と一行で報告して終える。

**3. 承認を待つ**

提示しただけで書き換えない。ユーザーの承認を得てから反映する。特に新しい訳語は、承認前に確定させない。ページごとに違う訳が生まれると、しずく的語彙が「しずくの言葉」であることが崩れる。

**4. 反映してパッケージし直す**

承認されたら該当ファイルを更新し、スキルフォルダ全体を `.skill` にまとめ直して、**ダウンロードできる形で提示する**。

```bash
cd <スキルフォルダの親ディレクトリ>
rm -f shizuku-wiki.skill
zip -rq shizuku-wiki.skill shizuku-wiki
```

更新したファイルと `.skill` の両方を提示する。ファイル単体は差分確認用、`.skill` は再インストール用として使い分けられる。

### 共有について

このスキルはしずくWikiの運用ノウハウそのものである。更新したら、GitHubやShizuku LabのDiscordで共有できる形にしておくと、他の編集者も同じルールで作業できる。承認後の反映時に、共有用に整えるかどうかをユーザーに確認するとよい。
