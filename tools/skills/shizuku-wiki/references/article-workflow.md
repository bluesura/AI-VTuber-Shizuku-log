# 記事の調査・編集・新規作成

配信ログから地の文を作る作業、連続企画の記事、新規ページ、動画・配信以外のAPI反映に使う。共通の記法は `SKILL.md`、文体は `tone-style-guide.md`、認証設定はスキルの `README.md` を正本とする。

## 1. 掲載先と現在の状態

対象ページの現在のソース・リビジョン・本文ハッシュを取得する。新規ページは正式名称と未作成を確認する。ページ名は公式の表記を優先し、提案時の「〈新規〉」などは名前へ含めない。

本人ページは概要、専用記事は詳説、ファン活動は参加導線、公式リンクはサービスの案内という粒度で分ける。専用記事を新設する場合も、既存ページの関連記述を調べて重複や矛盾を防ぐ。関連ページへのリンク追加は、公開する差分の範囲へ含めて確認する。

## 2. ログから根拠を集める

- 動画ID・日付を `.info.txt` で確認し、字幕の該当区間と前後の文脈へ戻る。連続企画は各回の展開に加えて、必要に応じて直後の振り返り配信・総集編・公式の告知も調べる。
- 本人の発言、一般視聴者の発言、公式アカウントのチャット、規約・公式発表を区別する。字幕の怪しい固有名詞・地名・話者は推測で確定せず、画面・音声・別の一次資料で補うか掲載を控える。
- 仕組みの説明は、画面で確認できたこと、本人が説明したこと、規約で案内されることを分ける。「記憶している」「忘れない」という語りから、永続保存や全サービス間の記憶共有を断定しない。
- 外部アカウント連携、思い出の保存、個別メッセージは、それぞれ確認できた範囲で書く。非公開のDMへアクセスしたり、私信を転載したりして裏付けを補わない。

調査用の区間メモには、主張、動画ID、時刻、参照ファイル、話者・資料の種別を残す。原本を訂正・整形して根拠と混ぜない。長い字幕は区間や論点ごとに読み、ツール出力が途中で切れていないことも確認する。

公式チャットを出典にするときは、動画の該当時刻へリンクし、出典中に「ライブチャット投稿：公式アカウント（時刻）」等と記す。しずくが音声で語った発言として扱わない。一般視聴者の表示名やIDは本文へ転記しない。

## 3. 文章と現在の参加可否

差分だけでなく、変更後の節全体を前後と続けて読み、段落の役割・文末・箇条書き・時系列を合わせる。既存の説明をつなぐ短い追記を優先し、同じ日付から始まる配信報告の段落を並べすぎない。新しい技術説明も、出典が支える範囲を保ちながら、読者が知りたい活動や体験として書く。

終了したリアルタイム企画では、当時の参加方法と現在可能なことを分ける。アーカイブで視聴できても、当時のコメント参加を再体験できるとは書かない。登録案内などは「配信当時」の説明と分かる形にし、サービス全体が終了したと誤読させない。現在の受付状況が確認できなければ推測しない。

画面上の関係・好感度などが確認できても、計算式・全ゲージの正式名称・固定の分岐条件まで分かったとは扱わない。専用記事は概要、遊び方・仕組み、各回の記録、アーカイブ、関連項目、出典など、内容に必要な節を選ぶ。新カテゴリ・テンプレートを無断で増やさない。

## 4. 差分と承認

差分を提示する前に、`editorial/QUALITY-GATES.md` と対象ページ固有の確認を済ませる。年表は `page-timeline.md` §7の意味的レビューを全追加・置換項目に行い、出典・判断理由・最終稿との対応を `editorial/workflow.md` の記録に残す。未審査の項目は公開候補から外す。

既存ページは追記・置換と挿入位置、新規ページは「追記（新規ページ）」として本文全量を示す。連動ページ・英語版の扱いも明記する。調査資料、確認案、承認された本文のハッシュ、保存結果は `outputs/shizuku-wiki/` などのGit管理外の作業領域へ置く。

公開は、表示済みの案に対するユーザーの承認後に行う。承認時に指定された修正は、その内容も含めて反映する。Botの許可待ちだけで止まっていた場合、設定完了の連絡後に同じ本文への承認を取り直さない。新しい対象や意味の変更、他者の編集との競合が生じた場合は、そこを確認する。

## 5. API反映

`scripts/update_videos_streams.py` の `apply` は「動画・配信」専用。他ページの汎用更新コマンドとして使わない。対象ページを限定した処理で、次を守る。Botの設定手順・ページ制限の確認は `README.md` を参照する。

1. 認証後に、対象ページの編集・新規作成の許可を確認する。新規作成権限と対象ページの許可は別に確認する。
2. 承認本文のハッシュ、対象ページ、基準リビジョンを照合し、`action=parse` 等で出典・表・リンクを確認する。年表の出来事を追加・置換する場合は、送信するページ本文と基準本文の差分から実際の変更項目を抽出し、全項目が審査済みの提案と一致することを確認して `audit --page timeline --timeline-review ...` を再実行する。Pythonが使えない場合は手動照合と理由を記録する。変更箇所を前後の項目と続けて読み、未審査・保留・審査後の本文変更があれば、承認済みでも再審査が済むまで反映を止める。承認時の修正にも適用し、承認範囲内なら既存の承認を引き継ぐ。
3. 既存ページでは反映直前にリビジョンと本文ハッシュを取り直し、`baserevid` 等で競合検査し、`nocreate` で意図しない新規作成を防ぐ。新規ページでは未作成を再確認し、`createonly` で先行作成を上書きしない。
4. 保存先の新リビジョンを記録し、可能なら匿名の読み取りでも保存本文と表示を確認する。エラーやタイムアウトで保存結果が不明な場合、再投稿する前に対象ページの履歴・本文を確認する。

保存本文の比較で不一致が出たら、まず実際の差分を調べる。MediaWikiが末尾の改行を除く例があるが、空白全体の削除などで差をまとめて無視しない。許容した差を記録し、送信本文と保存本文それぞれのハッシュを残す。

表示確認では出典エラー、内部リンク、カテゴリ、表の行を確認する。HTMLの属性値を調べる場合はHTMLパーサー等を使う。`cite&#95;note` のような文字参照を、単純な文字列検索だけで「出典がない」と誤判定しない。

年表の完了記録には、公開前の意味的レビューと公開後の本文・表示確認をそれぞれ残す。

## 6. 出典の保存と報告

出典URLのアーカイブを試し、保存先が確認できたもの、失敗、未実施を分けて記録する。HTTP 429などで制限されたら連続再試行を止め、未完了URLを残す。後日の再開では既存の記録と制限の解消を確認する。

完了報告には公開ページ・リビジョン、変更内容、確認結果、未完了事項を簡潔に含める。日本語版だけの公開なら英語版の未反映を記録する。アーカイブ保存の制限と、Wiki本文の公開成功を混同しない。

API仕様の参照：[MediaWiki API:Edit](https://www.mediawiki.org/wiki/API:Edit)。実行先のAPI応答で利用可能な機能を確認する。
